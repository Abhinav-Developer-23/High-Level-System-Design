3. Database Schema — Rules Table

Improvement over the original design: dropped the separate limit and window_seconds columns and moved their values inside rules too. Reason — those two columns only ever applied to fixed_window/sliding_window rows and sat NULL for token_bucket/leaky_bucket rows, so the table still had algorithm-specific columns mixed in with the generic ones. Putting every algorithm's parameters in rules means one column holds the config regardless of algorithm, so the app logic is just "read algorithm, then read rules" with no special-casing for which columns happen to be populated.

Every algorithm's parameters — even the simple ones like fixed window and sliding window — live in one flexible rules JSON column instead of separate typed columns. This keeps the row shape uniform: the app always reads algorithm to know which fields matter, then parses rules for that algorithm's specific parameters, no branching between real columns and JSON.

}

The limiter service reads algorithm first to know which fields matter, then parses rules for that algorithm's parameters — keeping one row shape for every algorithm instead of a different table per algorithm.

4. Redis Key TTL by Algorithm

TTL differs per algorithm because each one stores different state in Redis. Get it wrong in one direction and idle clients' keys never get reclaimed; get it wrong in the other and a key can expire mid-calculation, corrupting the count.

AlgorithmKey(s)TTLWhy
Fixed Window ratelimit:{client}:{route}:{windowStart} = windowSeconds (1×) Once the window passes, the counter is meaningless — expire it exactly when the window ends.
Sliding Window — counter variant current-window + previous-window keys = windowSeconds × 2 (2×) The previous window's count must still be alive for the weighted calculation while a request is inside the current window. At 1× TTL, the previous key can vanish mid-calculation.
Sliding Window — log variant ZSET of request timestamps ≈ windowSeconds (safety net only) ZREMRANGEBYSCORE actively trims stale entries on every request — TTL is just a backstop for a client that goes silent and stops triggering trims.
Token Bucket Hash {tokens, lastRefill} No strict requirement — soft TTL ≈ capacity / refillRate Refill math is time-elapsed based, so a stale key is still mathematically correct whenever it's next read. TTL here is purely memory cleanup for abandoned clients.
Leaky Bucket Hash {queueLevel, lastLeakTime} No strict requirement — soft TTL ≈ queueSize / leakRate Mirror of token bucket: the leak/drain calc is time-elapsed based, so a missing key just resets to an empty queue — harmless. TTL only reclaims memory.
Rule of thumb: only Fixed Window and Sliding Window have a TTL that affects correctness — too short and you can under-count or read a prematurely-expired window. Token Bucket and Leaky Bucket TTLs are purely memory hygiene, since their state self-corrects via elapsed-time math regardless of how stale the key is when read.

5. Back-of-the-Envelope Estimation

Sizing assumption: 10 million requests/sec average, across all clients.

1. Request volume 
Average:  10M req/s
Peak (3x factor for traffic spikes):
  10M req/s × 3 = 30M req/s
2. Unique / concurrent clients 
Active unique clients per day: 10M
Concurrency assumption:        10%
Concurrent clients = 10M × 10% = 1M
3. Rate limit check operations

Each request needs 2 ops against the counter store: 1 read (fetch current count) + 1 write (increment/update).

At peak: 30M req/s × 2 ops/req = 60M ops/sec

This is the sustained throughput the Redis cluster (or counter store) must handle.

Storage capacity is a non-issue; the real engineering challenge is sustaining 60M ops/sec at sub-5ms p99 latency, which is why the design leans on Redis sharded across multiple nodes rather than any exotic storage tier. This confirms the system is read-heavy and latency-sensitive, not memory-constrained.
