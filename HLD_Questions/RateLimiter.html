3. Database Schema — Rules Table

Improvement over the original design: dropped the separate limit and window_seconds columns and moved their values inside rules too. Reason — those two columns only ever applied to fixed_window/sliding_window rows and sat NULL for token_bucket/leaky_bucket rows, so the table still had algorithm-specific columns mixed in with the generic ones. Putting every algorithm's parameters in rules means one column holds the config regardless of algorithm, so the app logic is just "read algorithm, then read rules" with no special-casing for which columns happen to be populated.

Every algorithm's parameters — even the simple ones like fixed window and sliding window — live in one flexible rules JSON column instead of separate typed columns. This keeps the row shape uniform: the app always reads algorithm to know which fields matter, then parses rules for that algorithm's specific parameters, no branching between real columns and JSON.

ColumnTypeNotes
idUUID (PK)Row identifier.
route_patternVARCHAREndpoint this rule applies to, e.g. /api/orders/*.
tierVARCHAR, nullableSubscription tier (free, pro); null = applies to all tiers.
algorithmENUMfixed_window, sliding_window, token_bucket, leaky_bucket.
rulesJSON / JSONBAlgorithm-specific parameters for whichever algorithm this row uses (see samples below).
enabledBOOLEANLets ops disable a rule without deleting it.
updated_atTIMESTAMPDrives cache invalidation in the limiter service.
rules — fixed window row 
{
  "limit": 100,          // max requests allowed inside a single window
  "windowSeconds": 60    // window length in seconds; counter resets when a new window starts
}
rules — sliding window row 
{
  "limit": 100,          // max requests allowed within the trailing window
  "windowSeconds": 60    // length of the rolling window used for the weighted/log-based estimate
}
rules — token bucket row 
{
  "capacity": 50,        // max tokens the bucket can hold — i.e. the largest burst allowed
  "refillRate": 10,      // tokens added back per second once consumed
  "cost": 1              // tokens a single request consumes (default 1; expensive endpoints can cost more)
}
rules — leaky bucket row 
{
  "queueSize": 100,          // max requests allowed to sit queued at once
  "leakRate": 20,            // requests drained/processed per second, at a constant pace
  "overflowAction": "reject" // what happens once the queue is full: "reject" or "drop_oldest"
}

The limiter service reads algorithm first to know which fields matter, then parses rules for that algorithm's parameters — keeping one row shape for every algorithm instead of a different table per algorithm.
